## 동기 vs 비동기

**동기**

> 한 작업이 끝날 때까지 기다렸다가 다음 작업 처리

- 직관적인 흐름
- 디버깅 용이
- 다음 코드를 실행하기 전 외부 연동 결과가 필요한 경우

**비동기**

> 한 작업이 끝날 때까지 기다리지 않고 바로 다음 작업 처리

- 요청 흐름이 외부 연동의 지연 시간에 묶이지 않기를 바라는 경우
- 실패했을 때 재시도가 용이한 경우
- 연동에 실패했을 때 나중에 수동으로 처리할 수 있는 경우
- 연동에 실패했을 때 무시해도 되는 경우

## 비동기 전략

### 1. 스레드

- 스레드 풀 사용하기
- 프레임워크가 제공하는 비동기 기능 사용하기
  - Spring의 `@Async` (비동기 메서드는 예외를 전파하지 않으므로 트랜잭션에 주의)
  - FastAPI의 `run_in_threadpool`

스레드는 자체적으로 일정 크기의 메모리를 사용한다. 스레드 생성 시간, OS 레벨 컨텍스트 스위칭으로 인한 CPU 오버헤드가 발생한다.

스레드 풀을 사용하면 스레드를 일정 개수로 유지할 수 있어 메모리 사용량이 일정하게 유지된다. 하지만 스레드 풀에 생성한 스레드 개수보다 더 많은 작업을 동시에 실행하면 일부 작업이 다른 작업이 끝날 때까지 대기해야 한다.

### 2. 메시징 시스템

> 두 시스템 간 데이터 연동이 필요한 경우 사이에 위치해 데이터를 중계하는 시스템

**장점**

- 두 시스템이 서로 영향을 주지 않음
- 확장에 용이

**용어**

- Producer/Consumer
- Publisher/Subscriber

**주요 MQ**

- Kafka
  - 높은 처리량
  - 수평 확장 용이 (서버(브로커), 파티션, 소비자 확장)
  - 메시지를 파일에 보관해서 메시지가 유실되지 않음
  - 토픽-파티션 1:N 구조 (파티션 단위 순서 보장, 토픽 수준 순서 보장 X)
  - 소비자가 언제든 재처리 가능
  - Pull 모델 (소비자가 브로커에서 메시지를 읽어감)
- RabbitMQ
  - 클러스터로 처리량을 늘릴 수 있음
  - 메모리에만 메시지를 보관하는 큐 설정은 장애 상황 시 메시지 유실 초래
  - 메시지 큐에 등록된 순서대로 소비자에게 전송
  - 메시지가 소비자에게 전달됐는지 확인하는 기능
  - Push 모델 (브로커가 소비자에게 메시지를 밀어 넣음. 소비자 성능이 느려지면 큐 적체로 인한 성능 저하 발생 가능)
  - AMQP, STOMP 등 여러 프로토콜 지원
  - Pub/Sub, 요청/응답, Point-to-Point 패턴 지원
  - 우선순위를 지정해서 처리 순서 변경 가능
- Redis Pub/Sub
  - 메모리를 사용하므로 지연 시간이 짧음
  - RabbitMQ 대비 처리량이 높음
  - 구독자가 없으면 메시지 유실
  - 기본적으로 메시지가 영속되지 않음 (dump 설정 필요)
  - 단순함
- NATS, SQS, ...

#### 메시지 생성 측 고려 사항

1. **메시지 유실 가능성**
   - 무시
     - 사용하는 MQ의 특성과 메시지의 목적/중요성을 고려해 의도적으로 무시할 수 있음
   - 재시도
     - 네트워크 불안정
     - 중복 메시지 전송 처리 (MQ가 지원하지 않으면 소비자 측에서 핸들링)
   - 실패 로그 기록
     - 후처리에 필요한 데이터와 함께 DB 또는 파일에 남기기

2. **DB 트랜잭션 연동**

   DB 트랜잭션에 실패했는데 메시지가 발송되면 잘못된 데이터가 전달될 수 있음

   - 트랜잭션이 끝난 뒤(커밋 or 롤백)에 메시지 전송
   - DB에 데이터를 반영한 뒤에 메시지를 최대한 유실 없이 보내고 싶으면 트랜잭션 아웃박스 검토

#### 메시지 소비 측 고려 사항

1. **동일 메시지 중복 처리 가능성**
   - (수동적) 메시지 생산자가 같은 데이터를 가진 메시지를 메시징 시스템에 두 번 전송
     - 생산자가 메시지에 부여한 고유한 ID를 처리 전 확인해서 이미 처리됐는지 판단 (DB 조회, Set-메모리 상한 고려)
   - (능동적) 소비자가 메시지를 처리하는 과정에서 오류가 발생해서 메시지 재수신
     - 재시도 대상 API가 멱등성을 갖도록 구현

2. **메시지 소비 모니터링**
   - 소비자 성능 저하로 큐 적체가 발생하면 전체 성능 저하

#### 메시지 종류

- Command
  - 특정 수신자에게 특정 행동을 요청하는 메시지 (push)
  - 수신 측의 기능 실행에 초점
- Event
  - 정해진 수신자가 없음
  - 이벤트에 관심 있는 소비자가 메시지를 꺼내 읽음 (pull)

> **궁극적 일관성**
>
> 데이터를 즉시 모든 노드에 똑같이 맞추지 않지만 (불일치 시점 존재), 새로운 업데이트가 멈추고 일정 시간이 지나면 결국 모든 복제본의 데이터가 일치하게 되는 상태를 보장하는 성질

### 3. 트랜잭션 아웃박스

메시지 데이터가 유실되지 않도록 보장하기 위해 해당 데이터를 **DB에 안전하게 저장**하고, 저장된 메시지를 읽어 메시징 시스템에 전송하는 방법

하나의 DB 트랜잭션에 2가지 작업 수행

- 실제 업무 로직에 필요한 DB 변경 작업 수행
- 메시지 데이터를 아웃박스 테이블에 추가

아웃박스 테이블에 쌓인 메시지는 별도의 메시지 중계 프로세스가 주기적으로 읽어서 메시징 시스템에 전송

**발송 완료를 표시하는 방법**

- 아웃박스 테이블에 발송 상태 컬럼 두기 (`pending`, `done`, `failed`) → 모니터링 용이
- 메시지 중계 서비스가 성공적으로 전송한 마지막 메시지 ID를 별도로 기록 (파일, 별도 테이블)
  - 두 개 이상의 메시지 중계 서비스가 하나의 아웃박스 테이블을 함께 사용하는 경우, 각 중계 서비스가 고유하게 마지막 메시지 ID를 관리해야 함

**테이블 구조**

`id`, `message_id`, `messageType`, `payload`, `status`, `failCount`, `occurredAt`, `processedAt`, `failedAt`

`failed` 상태는 `memo` 컬럼을 추가해 실패 메시지를 아웃박스 테이블에 기록해 실패 이유 파악 가능 (반드시 후속 조치 필요)

### 4. 배치

> 데이터를 모아 두었다가 일정 간격으로 한 번에 전달하는 방식

| 방식 | 전달 시점 |
| --- | --- |
| 메시징 시스템 | 거의 실시간 |
| 배치 | 일정 간격 |

**처리 흐름**

1. DB에서 전송할 데이터 조회
2. 조회한 결과를 파일로 기록
3. 파일을 연동 시스템에 전송
   - FTP, SFTP (SFTP는 SSH 위에서 동작해 전송 구간이 암호화됨)

**파일 형식**

- delimiter: 구분자(콤마, 탭 등)로 값을 나눈 형식 (CSV 등)
- KV: `key=value` 형태
- JSON

**사전에 정해 둘 것**

- 송수신 주체
- 시간 (언제 만들고 언제 가져가는지)
- 경로 (파일이 놓이는 위치)

### 5. CDC

변경된 데이터를 추적하고 판별해서 변경된 데이터로 작업을 수행할 수 있도록 하는 소프트웨어 패턴
