## 우리는 문제가 없는데
외부 연동 서비스도 하나의 의존성으로서 문제가 발생하면 우리 쪽 서비스의 장애 원인이 될 수 있음.

## 타임아웃
- 여느 타임아웃과 비슷하게, 외부 API에 대해 타임아웃을 설정하지 않으면 해당 서비스가 응답하지 않을 때, 동시 요청 수가 증가하면서 서비스가 마비될 수 있음.

- 한마디로, 연동 서비스에 대해 타임아웃을 설정하지 않으면 연동 서비스의 응답이 느릴 때 처리량이 급증함.

- 사용자가 새로 고침으로 요청을 보낼 때마다 부하가 누적되면서, 서버에 부하가 걸림.

- 타임아웃을 걸어 두면, 사용자는 에러 화면을 보기는 하지만, 반응 없이 무한 대기하는 것보다는 나으며 연동 서비스 문제가 다른 기능에 주는 영향을 줄일 수 있음.

### 종류
> **Connection Timeout**
네트워크 연결 대기 시간
- 3~5초 권장, 추이에 따라 조정

> **Read Timeout**
응답 대기 시간 제한
- 5~30초 권장, 추이에 따라 조정
- 결제처럼 민감한 기능은 타임아웃 시간을 약간 길게 설정해서 정상적으로 처리할 수 있도록 보장해야 함.

## 재시도
> **재시도를 해도 되는 경우**
- 단순 조회 기능
- Connection Timeout
- 멱등성이 있는 변경 기능

- Read Timeout은 이미 서비스가 처리를 진행하는 중일 수 있기 때문에 재시도에 주의
- 멱등성: 연산을 여러 번 적용해도 결과가 달라지지 않는 성질

### 재시도 횟수와 간격
#### 재시도 횟수
- 대부분 1~2회면 충분

#### 재시도 간격
- 네트워크 일시적 이상의 경우, Connection Timeout이 발생하면 3초 뒤에 실행하는 식
- 지수 백오프: 연동 서버에 가해지는 부하 완화 가능

### 안티패턴: 재시도 폭풍
- 연동 서비스 입장에서는 우리 서비스가 클라이언트
- 계속해서 재시도를 보내면, 연동 서비스 서버 부하

## 동시 요청 제한
연동 서비스에 임계치 이상의 요청을 보내면서 발생하는 성능 저하 문제를 완화하는 방법 = 당연하게도 연동 서비스에 요청을 일정 수준 이상 보내지 않는 것

## 서킷 브레이커
> 연동 서비스가 장애 상황일 때는 연동 대신 바로 에러를 응답하고, 정상화되었을 때 연동을 재개하는 것

연동 서비스가 정상 상태가 아닐 때, 해당 서비스에 요청을 보내지 않고 바로 에러를 응답하는 것이 나음 (응답 시간 증가 및 처리량 감소 방어)

### 상태
- 닫힘
: 모든 요청을 연동 서비스에 전달
- 열림
: 지정한 임계치를 초과한 오류가 발생하는 경우

> 임계치 종류
- 시간 기준 오류 발생 비율 (10초 동안 오류 비율이 50% 초과)
- 개수 기준 오류 발생 비율 (100개 요청 중 오류 비율이 50% 초과)

열림 상태는 지정 시간 동안 유지
-> 이 상태에서는 연동 요청을 수행하지 않고 바로 에러 반환 (Fail Fast)

반 열림 상태가 되면 일부 요청에 한해 연동 시도
-> 일정 개수 or 일정 시간 동안 반 열림 상태 유지 -> 이 기간 동안에 연동에 성공하면 닫힘 상태로 복귀 -> 연동에 실패하면 다시 열림 상태로 전환

서킷 브레이커가 열려 있는 동안 연동 서버 회복 기회

## 외부 연동 & DB 연동

### 외부 연동과 트랜잭션 처리
**Case 1) 외부 연동에 실패했을 때 트랜잭션을 롤백**
- 외부 연동이 확실히 실패한 경우에는 단순히 트랜잭션 롤백
- 외부 연동이 Read Timeout으로 인해 트랜잭션을 롤백할 때는, 외부 서비스가 실제로는 성공했을 가능성이 있기 때문에 다음을 고려

  (1) 일정 주기로 두 시스템의 데이터가 일치하는지 확인하고 보정하기 (데이터 일관성이 중요한 경우)
  (2) 일정 시간 후에 이전 호출이 실제로 성공했는지 여부를 반환하는 API 호출하기
  -> Read Timeout 발생 후 일정 시간 뒤 취소 API 호출 응용 가능
 
**Case 2) 외부 연동은 성공했지만 DB 연동에 실패해 트랜잭션을 롤백**
트랜잭션을 롤백한 뒤 취소 API를 호출해 외부 연동을 이전 상태로 되돌려야 함.

### 외부 연동이 느려질 때 DB 커넥션 풀 문제
외부 연동 서비스의 지연 시간이 Connection 지속 시간에 포함되어 DB 커넥션 풀이 부족해지는 현상

- DB 연동과 무관하게 외부 연동을 실행할 수 있다면, DB 커넥션을 사용하기 전이나 후에 외부 연동을 시도하는 방안 고려.
-> 단, 이 경우 트랜잭션 범위 밖에서 외부 연동이 실행되므로, 트랜잭션 커밋 이후 외부 연동이 실패하면 롤백이 불가능하다는 점 고려해 후처리를 고안해야 함.
-> 후처리: 트랜잭션으로 반영된 데이터를 되돌리는 보상 트랜잭션

### HTTP 커넥션 풀
DB 커넥션 풀이 DB 연결에 걸리는 시간을 줄여 성능을 높이는 것처럼, HTTP 연결도 커넥션 풀을 사용하면 연결 시간을 줄일 수 있어 응답 속도 향상에 도움이 됨.

> **고려할 사항**
- HTTP 커넥션 풀의 크기
- 풀에서 HTTP 커넥션을 가져올 때까지 대기하는 시간
- HTTP 커넥션을 유지할 시간 (keep alive)

1) 풀의 크기는 연동 서비스의 성능에 따라 결정
2) 대기 시간은 수 초 이내의 짧은 시간으로 설정하기 (1~5초)
3) 커넥션 유지 시간  (Keep-Alive 헤더)
