## 처리량과 응답 시간
### 응답 시간
> 사용자의 요청을 처리하는 데 걸리는 시간(ms)

- TTFB: 응답 데이터 중 첫 번째 바이트가 도착할 때까지 걸린 시간
- TTLB: 응답 데이터의 마지막 바이트가 도착할 때까지 걸린 시간
- 로직 수행, **DB 연동**, **외부 API 연동**, 응답 데이터 생성/전송

### 처리량
> 단위 시간당 시스템이 처리하는 작업량

- **TPS**: 초당 트랜잭션 수
- RPS: 초당 요청 수

동시에 들어오는 요청 수가 최대 TPS를 초과하면 서버는 초과한 요청을 나중에 처리한다.

요청이 최대 TPS를 초과하면 응답 시간의 증가(사용자 이탈 가능성)로 이어질 수 있다.

#### TPS를 높이는 방법
1. 서버가 동시에 처리할 수 있는 요청 수를 늘려 대기시간 줄이기
2. 처리 시간 자체를 줄여 대기 시간 줄이기

단, 모니터링 도구를 통해 현재 서버의 TPS와 응답 시간을 정확하게 측정한 후에 목표 TPS와 응답 시간을 설정하고 성능 개선안을 도출해야 한다.

> "섣부른 최적화는 모든 악의 근원이다." - Donald Knuth

## 서버 성능 개선 기초
### 개선 전략 개요
트래픽 증가로 인한 성능 문제가 발생하는 주된 이유 = **시스템이 허용하는 최대 TPS 초과**

1. 성능 문제가 발생하는 지점 찾기
	- 처리 시간이 오래 걸리는 작업 식별하기
    - 모니터링 도구, 로그


2. 수직 확장 vs 수평 확장
	- 수직 확장: 장비 업그레이드 (비용 문제. 근본적 해결책은 아님.)
    - 수평 확장: 서버 늘리기 (로드 밸런서)


### DB 커넥션 풀
#### DB 작업 과정
> 1. DB 연결
2. 쿼리 실행
3. 연결 종료

서버와 DB는 네트워크 통신을 통해 연결되고, **쿼리 시간 못지 않게 연결을 생성하고 종료하는 데도 신경 쓰일 정도의 시간이 소요**된다.

#### DB 커넥션 풀
요청마다 매번 연결을 생성하고 종료하는 오버헤드를 줄이기 위해, DB에 연결된 커넥션을 미리 생성해서 보관하는 방법. 커넥션을 재사용하기 때문에 응답 시간이 줄어드는 장점이 있음.

##### 고려해야하는 설정
> - 커넥션 풀 크기 (min, max)
- 풀에 커넥션이 없을 때 커넥션을 구할 때까지 대기할 시간
- 커넥션의 유지 시간 (최대 idle 시간)

##### 1. 커넥션 풀 크기
- 가장 중요한 설정
- 커넥션 풀 개수를 초과하는 요청이 들어올 경우 커넥션을 얻지 못한 요청은 대기해야 함.
- min, max를 정해서 트래픽에 따라 유동적으로 관리 가능
- DB 서버의 CPU 사용률을 고려해서 신중하게 설정해야 함. (커넥션 풀을 늘리면 이론상 요청 당 응답 시간이 감소한다. 하지만, DB 서버 CPU 부하가 커져 포화 상태에 이르면 오히려 응답 시간이 증가할 수 있다.)
- 서버 수평 확장 = 커넥션 풀 늘리기
- 트래픽이 순간적으로 급증하는 패턴을 보인다면 커넥션 풀의 최소 크기를 최대 크기에 맞추는 게 유리함. (한꺼번에 시도하는 DB 연결에 드는 시간도 성능 저하의 주요 원인)

##### 2. 커넥션 대기 시간
- 풀에 사용할 수 있는 커넥션이 없을 때 커넥션을 얻기 위해 기다릴 수 있는 최대 시간. (ConnectionTimeoutError)
- 응답 시간이 중요한 서비스는 커넥션 대기 시간을 최대한 짧게 설정해서 빨리 실패하게 해야 서버 부하를 일정 수준으로 유지할 수 있음. (대기 시간이 길어지면 못 참고 다시 시도 하는 클라이언트의 재요청이 발생하면서 동시 트래픽이 더 증가하기 때문. 즉, 특정 타임 슬라이스에 몰리는 요청 수가 많아지는 걸 방지하기 위해 fail fast 하는 것이 좋다.)

##### 3. 최대 유휴 시간
- 사용되지 않는 커넥션을 풀에 유지할 수 있는 최대 시간
- N분 이상 사용되지 않은 커넥션은 종료되어 풀에서 제거됨.
- DB 서버에 설정된 비활성화 유지 시간보다 짧게 설정하면, DB 쪽에서 연결을 끊기 전에 서버 측 커넥션 풀에서 커넥션을 제거할 수 있음.

Stale Connection으로 인한 에러를 방지할 수 있는 설정
> - 최대 유휴 시간 지정
- 유효성 검사

최대 유지 시간: 생성된 시점으로부터 N 시간까지만 유효하도록 설정 (커넥션이 유효하더라도 종료 후 제거)

### 서버 캐시
캐시: (key, value) 쌍을 저장하는 Map과 같은 형태의 데이터 저장소

#### 캐시 히트, 삭제 규칙
> 캐시 적중률 (hit rate) = 캐시에 존재한 건수 / 캐시에서 조회를 시도한 건수

- **LRU**: 가장 오래전에 사용된 데이터 제거
- LFU: 가장 적게 사용된 데이터 제거
- FIFO: 가장 먼저 추가된 데이터부터 제거

오래된 데이터를 미리 삭제하거나, TTL을 설정해 메모리 효율적으로 사용하기

#### 로컬 캐시
- 인 메모리 캐시
- 서버 인스턴스 RAM 활용
- 빠르고 단순하다.
- 서버 프로세스 재시작 시 캐시 초기화로 인한 일시적 hit rate 감소, 서버 인스턴스 간 캐시 공유가 어렵다.

#### 리모트 캐시
- 예) AWS ElastiCache
- 로컬 캐시의 정반대의 장단점.
- 네트워크 통신이 기반이므로 지연시간 추가.
- 서버 프로세스과 캐시 내용물이 분리되어 관리되어 재시작 시에도 캐시 적중률 유지

#### 캐시 사전 적재
- 순간적으로 트래픽이 몰릴 것으로 예상하는 경우 응답 시간을 안정적으로 유지할 수 있는 전략

#### 캐시 무효화
- 원본 데이터와의 정합성을 위해서 적절하게 변경/삭제 정책 운용 필요
- 변경에 민감한 데이터는 리모트 캐시에 보관해야 함 (여러 대의 서버가 같은 값을 바라봐야 하기 때문)
- 변경에 민감하지 않고 데이터 크기가 작은 경우 TTL 설정 후 주기적 갱신이 유리

### GC와 메모리 사용
- 메모리를 많이 사용하고 생성된 객체가 많을수록 사용하지 않는 객체를 찾는 데 시간이 오래 걸림
- 대용량 파일 전체를 메모리에 올리기 보다는 스트림을 활용해 잘라서 읽어들이면 효율적인 메모리 사용 가능

### 응답 데이터 압축
데이터 전송 시간에 영향을 주는 요소
> - 네트워크 속도
- 전송 데이터 크기

- Accept-Encoding, Content-Encoding 응답 헤더 활용
- 텍스트 상의 응답에 유리
- 방화벽 설정 주의
- 트래픽 = 비용 문제와도 직결되므로 압축 적극적으로 고려

### 정적 자원과 브라우저 캐시
- 클라이언트 캐시 활용 (Cache-Control)
- 브라우저가 정적 자원을 다운로드하면, 해당 파일을 로컬 메모리나 디스크에 보관하고, max-age 안에 다시 로드하면 서버에 요청을 보내지 않으므로 서버 입장에서는 비용과 속도, 클라이언트 입장에서는 속도 면에서 이점

### 정적 자원과 CDN
- CDN(Content Delivery Network)
- 이미지, JS 같은 정적 자원을 CDN으로 제공해 오리진 서버의 부하를 줄일 수 있음.

### 대기 처리
- 동시에 수용할 사용자 수를 제한하고 나머지 사용자를 대기처리해서 안정적인 서비스 처리 가능 (수강신청, 티켓 예매 등)
