# 서버와 동시성
서버는 기본적으로 다수의 클라이언트의 요청을 동시에 처리
- 클라이언트 요청마다 스레드를 할당해서 처리
- 비동기 IO (논블로킹 IO)를 사용해서 처리

# 동시성 문제
> **Race Condition**
> 여러 스레드가 동시에 공유 자원(critical section)에 접근할 때, 접근 순서에 따라 결과가 달라지는 상황

## 잘못된 데이터 공유
- **프로세스 수준**: 인스턴스가 하나뿐인 싱글톤 객체가 있을 때, 멀티 스레드 환경에서 해당 객체가 동시에 사용되는 경우 의도하지 않은 동작 발생
- **DB 수준**: DB 데이터를 동시에 변경하는 경우 조회 순서에 따라 의도치 않은 동작 발생

# 프로세스 수준에서의 동시 접근 제어
## Lock (Mutex)
공유 자원에 접근하는 스레드를 한 번에 하나로 제한할 수 있는 동시성 제어 도구

1. Lock 획득
2. Critical Section 작업
3. Lock 반환

> **Critical Section**
> 동시에 둘 이상의 스레드나 프로세스가 접근하면 안 되는 공유 자원(메모리, 파일)에 접근하는 코드 영역

여러 스레드가 동시에 Lock 획득을 시도하면 그중 하나만 획득하고 나머지 스레드는 Lock이 해제될 때까지 대기

## Semaphore
자원에 대한 접근을 일정 수준으로 제한하고 싶은 경우 Semaphore를 사용해 동시에 실행할 수 있는 스레드 수를 제한 가능

1. 퍼밋 획득 (P, wait) -> 허용 가능 숫자 -1
2. 코드 실행
3. 퍼밋 반환 (V, signal) -> 허용 가능 숫자 +1

남아있는 퍼밋 개수가 0인 상태에서 퍼밋을 획득하려는 스레드는 다른 스레드가 퍼밋을 반환할 때까지 대기

- Binary semaphore
- Counting semaphore

> **Binary Semaphore는 Mutex와 같은가?**
> 하나의 스레드만 critical section에 접근할 수 있다는 결과는 같지만, 의도와 규칙이 다르다.

## ReadWrite Lock
### 문제 상황
Read시에도 일률적으로 Lock을 사용하면 데이터를 변경하지 않더라도 동시에 읽기 작업을 수행할 수 없기 때문에 Write 빈도 대비 Read 빈도가 높은 경우 읽기 성능이 떨어질 수 있음.

### 해결
- Write Lock은 한 번에 한 스레드만 획득 가능
- Read Lock은 한 번에 여러 스레드가 획득 가능
- 한 스레드가 Write Lock을 획득하면 해당 Lock이 반횐될 때까지 Read Lock을 획득할 수 없음
- Read Lock을 획득한 모든 스레드가 Read Lock을 해제할 때까지 Write Lock을 획득할 수 없음

-> 쓰는 동안 읽을 수 없고, 읽는 동안 쓸 수 없으며, 동시에 여러 스레드가 읽기 작업을 수행할 수 있음

## Atomic Type
### 문제 상황
일반적인 Lock은 여러 스레드가 동시에 실행할 때 Lock을 확보한 스레드를 제외한 나머지 스레드가 대기하므로 CPU 효율이 저하되는 단점 존재

### 해결
Atomic Type을 활용하면 내부적으로 **CAS** 연산을 사용하여 Lock 없이도 동시성 구현이 가능함

> **CAS (Compare And Swap)**
> 변수의 현재 값이 이전에 읽어 둔 값(기대값)과 같은 경우에만 새 값으로 교체하고, 다른 경우에는 교체하지 않고 실패를 반환하는 연산. 비교와 교체가 하나의 원자적 CPU 명령어로 수행되므로, 그 사이에 다른 스레드가 개입할 수 없음.

# DB와 동시성
> **Pessimistic Lock**
> 데이터에 먼저 접근한 트랜잭션이 Lock을 획득하는 방식

Lock을 반환할 때까지 다른 트랜잭션은 동일 레코드에 대한 Lock을 획득하지 못하고 대기

**분산 Lock**
여러 프로세스가 동시에 동일한 자원에 접근하지 못하도록 막는 기법

> **Optimistic Lock**
> 데이터를 조회한 시점의 값과 수정하려는 시점의 버전이 같은지 비교하는 방식

- CAS의 철학과 유사하며 DB 계층에서 version 컬럼으로 동시성 문제를 해결한다는 점이 다름
- 일단 데이터 변경을 시도하기 때문에 Lock을 대기하는 과정이 없다는 점에서 실패할 경우 사용자에게 더 빠르게 응답할 수 있다는 장점이 있음

## 외부 연동과 Lock
트랜잭션 범위 내에서 외부 시스템과 연동해야 하는 경우, Pessimistic Lock을 고려하는 것이 유리

-> Optimistic Lock은 충돌을 커밋 시점에 발견해서 롤백으로 해결하는데, 외부 시스템 호출은 롤백이 안 되기 때문

Optimistic Lock을 사용하고자 하는 경우, 트랜잭션 아웃박스 패턴을 적용해서 외부 연동을 처리하는 방법을 고려할 수 있음

## 증분 쿼리
애플리케이션에서 값을 조회해 계산한 뒤 덮어쓰는 대신, 현재 값을 기준으로 한 연산을 UPDATE 문 하나로 DB에 위임하는 방식

-> DB는 해당 행에 쓰기 Lock을 건 상태에서 최신 값을 읽고 갱신하므로, 조회와 수정 사이의 틈이 사라져 Lost Update가 발생하지 않음 (단, 새 값을 단일 쿼리로 계산할 수 있는 경우에만 적용 가능)

# Lock 사용 시 주의사항
1. 잊지 않고 Lock 반환하기
2. 대기 시간 지정하기
3. Deadlock 피하기
   - 잠금 대기 시간 제한
   - 지정한 순서대로 Lock 획득하기

> **Livelock**
스레드나 프로세스가 멈추지는 않았으나 실제로는 아무것도 하지 않는 상태
-> 우선 순위를 두는 방식으로 해소 가능

> **Starvation**
> 프로세스나 스레드가 자원을 할당받지 못해 실행되지 못하는 상태
> - 우선 순위가 높은 작업이 많아 우선 순위가 낮은 작업이 실행되지 않는 경우
> - 특정 자원을 한 프로세스가 긴 시간 동안 독점하고 있어 다른 프로세스가 자원에 접근하지 못하는 경우
