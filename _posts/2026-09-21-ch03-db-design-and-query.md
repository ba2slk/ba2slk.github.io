## DB는 성능의 핵심
> full scan: 테이블의 모든 데이터를 순차적으로 읽는 것. 보통 쿼리의 where 절에 있는 조건에 대응하는 인덱스가 없을 때 발생.

## 조회 트래픽과 인덱스
- 조회 트패픽과 패턴에 따라 인덱스를 생성할 컬럼을 전략적으로 선택해야 한다.
- Full Text Search 인덱스
```sql
select id, title
from article
where title like `%검색어%` order by id desc limit 10;
```
이렇게 쓰면 full scan을 유발한다 (B-Tree 인덱스 동작 방식이 주요 원인). PostgreSQL `pg_bigm` + `GIN 인덱스`를 사용하면 full scan 없이 검색 쿼리를 실행할 수 있다.

### B-Tree vs GIN

**B-Tree**
- 행 하나에 키 하나. 
- 값을 통째로 정렬해 두는 인덱스라 `=`, 범위, `ORDER BY`, 전방일치 `LIKE 'abc%'`에 강하다.

**GIN (Generalized Inverted Index)**
- 행 하나에 키 여러 개. 
- 컬럼 값 안의 원소(배열 요소, JSON 키, 문자열 조각 등)를 뽑아 "원소 → 행 목록" 형태로 저장하는 역색인이라 `LIKE '%abc%'`, 배열/JSONB 포함 검색에 강하다.

![](https://velog.velcdn.com/images/fundev/post/bb7596b8-317e-4d42-8046-978e87c2f01a/image.png)

**pg_bigm**
문자열을 2글자씩 잘라 GIN에 넣는 확장. 검색어도 똑같이 잘라 조각을 모두 가진 행을 인덱스에서 뽑으므로 `%`가 앞에 붙어도 인덱스를 탈 수 있다.

### 단일 인덱스와 복합 인덱스
#### 단일 인덱스
- `userId`만 인덱스로 활용

#### 복합 인덱스
- `(userId, activityDate)`를 인덱스로 활용

마찬가지로 조회 패턴과 트래픽을 고려해야 한다. activityDate에 관한 조회 트래픽(쿼리 실행 빈도)이 많지 않다면 굳이 인덱스에 넣을 필요가 없다.

### 선택도를 고려한 인덱스 칼럼 선택
> **선택도**
'인덱스'에서 특정 칼럼의 고유한 값 비율

**선택도가 높을수록** 인덱스를 이용한 조회 효율이 높아진다.
- 선택도가 높다 = 값이 다양해서 조건으로 걸면 행이 확 줄어든다.
- 선택도가 낮아도(예: is_deleted -> false: 99%, true: 1%), is_deleted true를 찾는 쿼리 패턴이 압도적으로 많다면 인덱스를 설정하는 게 유리하다.

선택도는 어떤 컬럼이 인덱스 후보인가를 보는 지표일 뿐, 결국 **어떤 쿼리가 어떤 값을 얼마나 자주 찾느냐에 달려있다.**

### 커버링 인덱스
> **커버링 인덱스**
특정 쿼리를 실행하는 데 필요한 컬럼을 모두 포함하는 인덱스

실제 테이블에서 데이터를 읽어오는 과정이 생략되므로 쿼리 실행 시간이 빨라진다.
```sql
select activityDate, activityType
from activityLog
where activitiyDate = '2024-07-31' and activityType = 'VISIT';
```

### 인덱스는 필요한 만큼만 만들자
- 새로 추가할 쿼리가 기존에 존재하는 인덱스를 사용할 수 있는지 먼저 확인하기
- 새로 추가할 쿼리가 기존 인덱스를 사용하지 않는 경우, 요구사항을 일부 변경할 수 있는지 검토하기 (판단 기준을 바꿔보자)
- 같은 컬럼에 대한 인덱스를 또 추가하지 말자 (저장공간 낭비 및 유지보수 부채)

## 조회 성능 개선 방법
### 1. 미리 집계하기
비정규화를 통해 derived column을 미리 만들어 놓는 방법
- count, sum과 같은 집계 쿼리를 조회 시점에 실행하면서 발생하는 성능 문제 제거 가능
- 동시성 문제를 방어 및 검증

### 2. 페이지 기준 목록 조회 대신 ID 기준 목록 조회 방식 사용하기

#### 문제 상황
10만 개의 레코드가 있는 테이블에서 9만 9991 번째 레코드에 접근하고 싶다. DB는 어떤 id 값이 해당 위치에 있는지 모르기 때문에 역순으로 id를 9만 9990개 세고 나서 10개를 조회하게 되고, 그 시간만큼 실행 시간이 증가한다.

```sql
select id, subject, writer
from article
order by id desc
limit 10 offset 99990;
```

#### 해결
특정 ID 기준으로 조회한다.
```sql
select * from article
where deleted = false
order by id desc
limit 10;
```

### 3. 조회 범위를 시간 기준으로 제한하기
```sql
select title, author
from news
where regdt >= '시작 날짜' and regdt < '마지막 날짜'
order by regdt desc
limit 100;
```
regdt 컬럼에 인덱스를 추가하는 식이다.

- 최신 데이터만 조회하는 방식으로 성능을 높일수도 있다. DB가 사용하는 메모리 캐시의 hit rate에도 좋은 영향을 줄 수 있다. 캐시 효율이 좋아지면 응답 속도도 빨라진다.

### 4. 전체 개수 세지 않기
데이터가 많아질수록 count 실행 시간도 증가하므로 전체 개수를 화면에 표시하지 않는 방향으로 협의하는 등 조회 속도가 느려진다면 고려할만하다.
```sql
select count(*)
from member
where name like '민수%';
```

### 5. 오래된 데이터 삭제 및 분리 보관하기
쿼리 실행 시간은 데이터 개수에 비례한다.
- 데이터 개수 증가 폭 낮추기

과거 데이터 삭제
- 로그인 시도 내역 (최근 6개월만 저장하는 방식)

## 알아두면 좋은 것들
### 쿼리 타임아웃
응답 지연으로 인한 재시도는 서버 부하를 더욱 가중시키므로, 서비스와 기능의 특성에 따라 적절한 쿼리 타임아웃을 설정함으로써 서버 부하를 관리할 수 있다.

### 상태 변경 기능은 복제 DB에서 조회하지 않기
Main - Replica 구조에서
1. 두 DB의 데이터가 순간적으로 일치하지 않을 수 있다.
2. 트랜잭션 문제가 발생할 수 있다.
  - Main과 Replica 간 데이터 복제는 트랜잭션 커밋 시점에 이루어진다. 주 DB의 트랜잭션 범위 내에서 데이터를 변경하고, 복제 DB에서 변경 대상이 될 수 있는 데이터를 조회하면 데이터 불일치로 인해 문제가 발생한다.
  - INSERT, UPDATE, DELETE 쿼리를 실행하는 기능에서 변경 대상 데이터를 조회해야 한다면, 복제 DB가 아니라 Main DB에서 SELECT 쿼리를 실행하자.
  
### 배치 쿼리 실행 시간 증가
- group by, count, sum으로 집계를 구하는 경우
- 배치에서 사용하는 쿼리의 실행 시간을 지속적으로 추적해야 한다.
- 커버링 인덱스를 활용한다.
- 데이터를 일정 크기로 나눠 처리한다. (1달 분량 -> 1일 분량 x 30)

### 타입이 다른 컬럼 간 조인 주의
- 비교하는 컬럼의 타입이 달라서 인덱스를 활용하지 못하는 문제
- 두 컬럼의 타입을 맞춰서 비교해서 발생

### 테이블 변경은 신중하게
- 서비스 장애 발생 가능성
- (MySQL) 테이블 변경 시 새 테이블을 생성하고, 원본 테이블의 데이터를 복사한 뒤, 복사가 완료되면 새 테이블로 대체 -> 이 과정에서 UPDATE, INSERT, DEDLETE 같은 DML 작업을 허용하지 않기 때문에 복사 시간만큼 서비스 중단

### DB 최대 연결 개수
- 서버를 수평확장 했다고 하더라도 DB의 최대 connection 개수가 서버 측 connection pool 개수보다 적은 경우 연결 실패가 발생할 수 있다.
- DB 서버의 CPU 사용량 지표를 토대로 연결 개수를 조정할 수 있다. (캐시 서버 구성, 쿼리 튜닝 등 다른 방안 고려)

## 실패와 트랜잭션 고려하기
- 비정상 상황에서의 트랜잭션 처리를 반드시 고민해야 한다 (데이터 일관성 문제).
- 기능에 맞게 트랜잭션 경계를 적절히 나눠야 한다.
- 오류가 발생하면 롤백하는 게 일반적이지만, 항상 그런 것은 아니다. 회원가입 성공 축하 이메일 발송이 실패한 경우 성공한 회원가입도 모두 롤백 해야할까?
- 외부 API 연동과 DB 작업이 섞이면 트랜잭션 처리가 복잡해지는데, 4장에서 다룬다.
